New in v2 2.0.0

FrostByte v2 keeps everything that made v1 effortless — one script tag, zero servers, live matchmaking — and adds two big capabilities plus a brand-new midnight look. If you are upgrading from v1, nothing breaks: the core Play API is unchanged, so existing games keep working exactly as before.

  • 🌙 Lua multiplayer (play-lua.js). Embed the Fengari Lua VM in your page and drive the entire FrostByte API from Lua code through a net.* table — net.host(), net.broadcast(), net.on('data', fn)… Your game logic can now be written in Lua while the transport stays the same P2P WebRTC mesh. See Lua multiplayer.
  • 🔑 API keys with usage tracking. Generate keys, allow-list the site URLs each key may be used on, and every connection records the exact page URL it came from. Manage everything in the API Keys dashboard. See API keys.
  • 🌌 Midnight theme. The whole site and every template moved to a dark violet/magenta palette — deliberately not blue — with animated gradient frames, scanlines and breathing glows.
Upgrading: change your script URL to play.js on this site (it now serves v2) and you're done. Keys are optional — new Play({ game }) works exactly like it did in v1.

Getting started 2 min

FrostByte connects players browser-to-browser over WebRTC. There is no server to rent, no API key to paste and no account to create. The only thing you add to your game is one <script> tag — after that, your page effectively becomes the live server. This page shows every step of connecting a game with JavaScript.

1 · Include play.js

Put this tag in your HTML before your game code. The WebRTC engine (PeerJS) loads itself on demand from a CDN, with an automatic jsDelivr fallback.

index.html
<script src="https://gefrus112.github.io/FrostByte/play.js"></script>

2 · Create a game handle

The game namespace isolates your rooms from every other FrostByte game in the world, so pick something unique, like your game's name. All other options are optional.

game.js
const game = new Play({
  game: 'my-unique-game',     // your namespace (required)
  playerName: 'ace',          // nickname other players see
  debug: true                 // console logs while developing
});

3 · Connect

Three ways in — auto-matchmaking for strangers, or private room codes for friends:

game.js
// A) auto matchmaking — same network → same country → worldwide
await game.quickMatch();

// B) host a private room, share the 4-char code
const { code } = await game.host();      // e.g. "K7XF"

// C) join a friend's room
await game.join('K7XF');

4 · Sync your game

Send anything JSON-serializable. The data event fires on every other player's side, in milliseconds:

game.js
game.onData = (data, from) => {
  // from = { id, isHost }
  if (data.type === 'move') movePlayer(from.id, data.x, data.y);
};

// broadcast to everyone (host → all, guest → everyone via relay)
game.broadcast({ type: 'move', x: 128, y: 240 });
That's the whole integration. Open your game in two browser tabs (or send the link to a friend), press quick match in both — you're playing multiplayer. Check the Pong template for a complete, working reference.

Core concepts architecture

  • Host & guests (star topology). Every room has one host. Guests talk to the host; the host relays guest→guest traffic. For 2-player games this is invisible — it just feels direct.
  • Signaling vs. game data. The free public broker is used only to exchange connection offers (signaling). Once the WebRTC data channel opens, all game data flows directly between browsers — never through a server.
  • Room codes. host() mints a 4-character code from a confusion-free alphabet (no 0/O/1/I/L). The code maps to a namespaced broker id, so different games can't collide.
  • Heartbeats. The host pings every 3 s and prunes silent players after ~11 s; guests monitor the host symmetrically and raise an error event when the link dies.
  • Serializable payloads. Anything JSON-serializable works — plain objects, arrays, numbers, strings. Send small state diffs at 20–30 Hz for smooth gameplay.

Constructor new Play(opts)

Play works with or without new: new Play({...}) and Play({...}) are identical. The brand alias FrostByte points to the same object.

OptionTypeDescription
gamestringRequired. Your namespace, e.g. 'pong'. Lowercase letters, digits, -, _. Rooms never collide between different namespaces.
playerNamestringNickname shown in the roster and join events (max 16 chars).
apiKeystringNew in v2. A FrostByte key (fbk_live_…). Validated against the local key registry and its site allow-list; successful connections record the page URL they came from. Optional — see API keys.
debugbooleanVerbose console logging of every status change.
peerConfigobjectSelf-hosted signaling broker config, e.g. { host:'broker.me', port:443, path:'/', secure:true }. See Self-hosting.
onReady / onStatus / onData / onPlayerJoin / onPlayerLeave / onErrorfunctionShortcut event handlers — same as calling game.on(event, fn). See Events.
full example
const game = new Play({
  game: 'space-hockey',
  playerName: 'nova',
  onReady:    ({ isHost, code, scope }) => console.log('connected!', isHost, code, scope),
  onStatus:   (state, detail) => hud.textContent = detail,
  onPlayerJoin: p => console.log(p.name, 'joined'),
  onPlayerLeave: p => console.log(p.name, 'left'),
  onData:     (d, from) => applyState(d, from),
  onError:    err => showError(err.message)
});

Methods game.*

MethodReturnsDescription
quickMatch()Promise<{ isHost, scope }>Auto-matchmaking: probes "same network" → "same country" → "worldwide" slots, then hosts one if empty. See Matchmaking.
host()Promise<{ code }>Opens a private room and resolves with its 4-char code. You are the host; share the code.
join(code)Promise<{ code }>Joins a private room. Throws (with a friendly message) if the room doesn't exist.
send(data, toId?)voidHost: broadcast to all, or to one guest with toId. Guest: to everyone (relayed), or private to one player with toId.
broadcast(data)voidAlias of send(data) — reads nicer when you always mean "everyone".
players()ArrayLive roster: [{ id, isHost, name }], host first.
close()voidLeaves/destroys the room, clears timers. Call on beforeunload for instant leave.

Handy properties: game.isHost (boolean), game.code (room code or null in quick match), game.me ({ id, isHost, name }), game.version.

Events game.on(...)

EventPayloadFires when…
ready{ isHost, code, me, scope }The connection is live: room open (host) or joined (guest). scope is 'private' or the matchmaking scope that hit.
status(state, detail)Progress updates: region → searching → waiting → joining → connected → hosting → disconnected. Drive your HUD from this.
playerjoin{ id, isHost, name }A player finished joining (both sides see it).
playerleave{ id, isHost, name }A player left or timed out.

events
game.on('status', (state, detail) => {
  if (state === 'searching') splash.textContent = detail;  // "looking for players · US"
});
game.on('data', (d, from) => console.log('got', d, 'from', from.id));

Lua multiplayer play-lua.js

play-lua.js embeds the Fengari Lua VM (loaded from CDN, ~100 KB) and exposes the whole FrostByte API to Lua through a net table. Your networking code can now be written entirely in Lua, while data still travels over the same P2P WebRTC mesh as every other FrostByte game. JavaScript and Lua can call each other freely — JS calls Lua functions, Lua touches the DOM back.

1 · Include both scripts

play.js first (it is the transport), then play-lua.js (it is the bridge):

index.html
<script src="https://gefrus112.github.io/FrostByte/play.js"></script>
<script src="https://gefrus112.github.io/FrostByte/play-lua.js"></script>

2 · Write multiplayer in Lua

Run Lua from JavaScript with FrostByte.lua(source, opts) (or FrostByteLua.run) — it resolves with { ok, error, api }:

game.js
const res = await FrostByte.lua(`
  net.init({ game = 'my-lua-game', player = 'mo' })
  net.on('data', function (d, from)
    print('got', d.text, 'from', from.id)
  end)
  net.quickmatch()
  net.broadcast({ text = 'hello from Lua!' })
`, { globals: { ROOM: 'K7XF' } });

// call Lua functions from JavaScript any time:
res.api.call('on_button_pressed', 42);

Or drop a Lua file straight into the page — <script type="text/lua"> blocks are executed automatically once the VM is ready:

inline Lua
<script type="text/lua">
  net.init({ game = 'my-lua-game' })
  net.host(function (code) print('room code: ' .. code) end)
</script>

3 · Lua touches the DOM with js.run

ui.lua
net.on('playerjoin', function (p)
  js.run('hud.flash("' .. p.name .. ' joined")')
end)

The Lua Chat template is a complete working example — the entire networking layer of a chat room in ~60 lines of Lua.

How it fits together: Lua calls net.* → the bridge calls the same JS API from v1 → WebRTC does the transport. Tables cross the boundary both ways as plain JSON-able data, so { x = 1, tags = {'a','b'} } in Lua is { x: 1, tags: ['a','b'] } in JavaScript.

Lua API reference net.*

Everything below is available inside Lua once play-lua.js is loaded. Networking functions mirror the JavaScript API — same semantics, Lua-style.

Lua callReturnsDescription
net.init(cfg)—Connect the bridge: { game = 'name', player = 'mo', apiKey = 'fbk_live_…', debug = false }. Creates the underlying Play instance.
net.quickmatch(cb?)—Auto matchmaking. Callback: cb(isHost, scope) or cb(nil, errorMessage). The ready event also fires.
net.host(cb?)—Host a private room. Callback: cb(code) — e.g. "K7XF" — or cb(nil, err).
net.join(code, cb?)—Join a room by code. Callback: cb(code) or cb(nil, err).
net.broadcast(value)—Send to everyone. value may be a table, string, number or boolean.
net.send(value, toId)—Private message to one player id.
net.players()tableRoster: { { id='…', isHost=false, name='mo' }, … }, host first.
net.me()tableYour own { id, isHost, name }, or nil before connecting.
net.code()stringThe 4-char room code, or nil in quick match.
net.ishost()boolAre you the host of this room?
net.close()—Leave and tear everything down.
net.on(event, fn)—Subscribe: 'data' (data, from), 'status' (state, detail), 'ready' (info), 'playerjoin' (p), 'playerleave' (p), 'error' (e). Multiple handlers per event are fine.
net.version()stringBridge + library versions.
js.run(code)—Execute a JavaScript string — your escape hatch to the DOM.
js.stringify(v)stringJSON-encode a Lua table (handy for js.run).

From the JavaScript side, res.api exposes call(name, …args) (invoke a Lua global function and get its return value), get(name) / set(name, value) for globals, and close().

API keys Play.keys — v2

Keys let you gate and monitor who uses your FrostByte integration. Generate a key, allow-list the site URLs it may be used on, and hand it to your pages via the apiKey option. Every successful connection then records the site origin and the full page URL it was used from, plus a timestamp and running use count — all visible in the API Keys dashboard.

Manage keys from JavaScript

keys.js
// create — allow every site, or list specific origins
const key = Play.keys.create({
  name: 'Neon Pong — production',
  origins: ['https://neonpong.pages.dev', 'https://*.mysite.org']
});
console.log(key.key);            // 'fbk_live_x9…' — share with your pages

Play.keys.list();                // all key records + usage info
Play.keys.get('fbk_live_…');     // one record
Play.keys.revoke('fbk_live_…');  // block it (restore() re-enables)
Play.keys.del('fbk_live_…');     // delete the record
Play.keys.usage(20);             // last 20 usage events, newest first
Play.keys.clearUsage();          // wipe the log

Use a key in your game

game.js
const game = new Play({
  game: 'neon-pong',
  apiKey: 'fbk_live_x9y8…'
});

game.onError = err => {
  if (err.type === 'key') banner.textContent = err.message;
};

What gets validated, and when

  • Format — keys look like fbk_live_<24 random chars>.
  • Registry — the key must exist in this browser's registry (created via Play.keys.create() or the dashboard).
  • Status — revoked keys are rejected with a friendly error event (err.type === 'key'), and host()/join()/quickMatch() refuse to run.
  • Site allow-list — the current location.origin must match one of the key's origins ('*' allows all; https://*.mysite.org allows subdomains). This is how the dashboard knows which URL/site the API is being used from.
  • Usage recording — on every successful connect, the key's lastUsed, usedOn (site origin) and usedFrom (full page URL) are updated and an entry is appended to the usage log.
Honest serverless note: FrostByte has no backend, so keys live in localStorage of the browser that created them, and validation runs inside play.js on the client. That is perfect for tracking usage per site, gating your own deployments and revoking access — but it is not DRM: someone editing your page's source could bypass a local check. For hard guarantees, pair keys with your own broker (self-hosting) that inspects an auth token.
Keys are optional. new Play({ game }) without apiKey behaves exactly like v1 — free, open matchmaking for everyone. Use keys when you want the oversight.

Matchmaking quickMatch()

FrostByte's matchmaking is fully serverless — it works by probing short, deterministic room ids on the free broker, so there is no matchmaker service to run or pay for. When you call quickMatch(), the library:

  1. Detects your region — public IP, country code, and a fingerprint of your network (hash(ip)).
  2. Scans "same network" slots first. Players behind the same router share the fingerprint, so two tabs on your Wi-Fi match instantly with near-zero latency. Great for couch-style testing.
  3. Then scans your country's slots (e.g. every US quick-matcher probes the same 5 slot ids), keeping matches local and low-latency.
  4. Falls back to worldwide slots so matchmaking always eventually finds someone.
  5. If nobody is waiting, you become the host of the first free slot. The next searcher connects to you — usually within seconds. Status events tell you exactly where the search is: "looking for players · same network" → "… · US" → "… · worldwide" → "waiting for a challenger · US".
matchmaking HUD
await game.quickMatch();
// → status events while searching:
//    region     "checking your region…"
//    searching  "looking for players · same network"
//    searching  "looking for players · US"
//    searching  "looking for players · worldwide"
//    waiting    "waiting for a challenger · US"   (you are the host now)
// → 'ready' event when matched:
//    { isHost: false, code: null, scope: 'same network' }

Limitations (honest ones)

  • Two simultaneous first-searchers can both fail to find each other (both scan, nobody hosts yet) and end up hosting separate slots. The next pair will match fine. For tournaments, prefer host() + codes.
  • Country matching is best-effort — it's IP geolocation, not GPS. VPNs put you in another country; that's a feature if you want worldwide matches.
  • "Same network" means "same public IP". Big carrier-grade NATs (mobile networks) may group strangers together — rare, and harmless: worst case you play a Pong with a neighbour.
Tip: show the scope in your UI ("matched · same network 🎉"). Players love knowing the match is local — and it sets expectations for latency.

Data patterns recipes

Guest → host input, host → all state

The classic real-time pattern (used by the Pong template): guests send only their inputs; the host simulates the world and broadcasts snapshots.

authoritative host
// GUEST — send input at ~30 Hz
setInterval(() => game.send({ t: 'pad', y: myPaddleY }), 33);

// HOST — simulate + broadcast at ~30 Hz
setInterval(() => {
  stepPhysics(guestPadY);
  game.broadcast({ t: 's', ball, pads, score });
}, 33);

// GUEST — render from snapshots
game.onData = (d) => { if (d.t === 's') render(d); };

Turn-based games (cards, chess, trivia)

Even simpler — broadcast the move, everyone applies it in order:

turn sync
function playCard(card) {
  game.broadcast({ t: 'move', card, by: game.me.id });
}
game.onData = (d) => { if (d.t === 'move') applyMove(d); };

Private messages (guest → specific guest)

whisper
const other = game.players().find(p => p.id !== game.me.id);
game.send({ t: 'taunt', text: 'nice miss!' }, other.id);

game.onData = (d, from) => {
  if (d.t === 'taunt') chat.log(`⚠ ${from.id}: ${d.text}`);
};
Keep payloads small. Send input/state changes, not full world dumps, and stay under ~30 messages per second per player. WebRTC data channels are unordered & reliable here — perfect for game state, but not a torrent client.

Self-hosting your own broker

FrostByte rides on the free public PeerJS cloud by default. If you want your own signaling (privacy, regions, or the cloud having a bad day), run the open-source peerjs-server on any free tier (Fly.io, Render, Railway, a $4 VPS…) and point peerConfig at it:

own broker
const game = new Play({
  game: 'my-game',
  peerConfig: { host: 'my-broker.fly.dev', port: 443, path: '/', secure: true }
});

Everything else — matchmaking, room codes, events — works identically, because FrostByte only ever talks the standard PeerJS protocol.

FAQ quick answers

Is it really free? What's the catch?
Yes. Game data flows directly between browsers (WebRTC), so there is no traffic bill. The public broker does introductions for free — the same infrastructure PeerJS has offered for years. The catch-free path is also the open-source path: self-host the broker if you ever want to.
How many players per room?
Tested comfortably at 2–8 in a star topology. The host relays guest→guest traffic, so CPU/network cost grows linearly. For a 2-player game (the sweet spot for Pong-likes) it's essentially a direct cable.
Does it work on GitHub Pages / itch.io / Neocities?
Anywhere a modern browser opens your page — including this very site, which is plain static hosting. WebRTC doesn't care where the HTML came from.
Mobile support?
Yes — WebRTC data channels run in mobile Safari/Chrome. The Pong template ships touch controls; add game.close() on pagehide for clean leaves.
Is my game data visible to FrostByte or PeerJS?
No. The broker only sees encrypted connection setup (ids, SDP offers). Payloads travel on the direct P2P data channel, encrypted by DTLS end-to-end.
How do I test multiplayer alone?
Open the game in two tabs. Quick match will pair them via the "same network" scope in a second or two — that's the scope doing its job.

Troubleshooting when frost bites

  • "Room not found" — the host closed the tab, or the code was mistyped. Codes are 4 chars from an alphabet without 0/O/1/I/L.
  • "signaling broker timeout" — a corporate firewall is blocking WebRTC signaling. Try another network, or set peerConfig to your own broker on port 443.
  • "WebRTC connection failed (strict NAT)" — some enterprise/carrier NATs block direct links. Hosting your own TURN-enabled broker fixes it; most home networks are fine.
  • Matchmaking feels slow — it's probing empty slots. Empty-slot probes fail in ~100 ms, but slow geo APIs can add a moment. If Play.region() fails, you'll match worldwide only.
  • PeerJS CDN blocked? — play.js already falls back from unpkg to jsDelivr. Offline? Nothing can save us — the engine needs the internet to say hello.
Still stuck? Turn on debug: true, watch the console, and open an issue at github.com/gefrus112/FrostByte/issues.
